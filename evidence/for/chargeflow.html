Agent dispute evidence

A constructed agent card dispute, mapped to the evidence playbook

Read this first

Prepared for the Chargeflow team. As of 2026-10-26, Chargeflow has not reviewed or endorsed this page, and no page or menu on this site links to it.

The case on this page is a constructed test case. A script built the signed log with a test key; only the witness receipts are live, signed by Headless Oracle's witness on 25 October 2026; and each card charge time is a test value, the receipt's time plus 60 seconds written to the whole second, so the check that the witness receipt's time is before the charge time passes by construction. No real order was placed, no card was charged, and no AI agent or gate ran. The limits below are the verifier's standard wording for a log of this format; here Headless Oracle holds the test key and a script built the log. The case page linked below says how it was built.

The example's own limit:

in WE-4, Headless Oracle is the gate's operator (it runs the gate and holds the operator key) and the witness, and the customer, the merchant and the charge are test parties the example makes. The example demonstrates the format and the checks, not independence between those parties (L14, L3). The card data is test data only: no card number, expiry, security code, network token or last four digits appears in the bundle, in the stated inputs, on the page or on the exhibit, because B-CARD reads none of them; the charge id and every merchant and item value are labelled test values (`TEST`, and the domain `test-merchant.example`, under the `.example` name reserved for examples).

limittext
L24v0.10. For a card payment, the payment proof is the card network's authorization record, which the issuer holds; this bundle neither carries nor verifies it. What this verdict shows is whether the decision and the order the gate recorded were witnessed before the charge's authorization time as stated, and whether that order matches the stated charge: the stated charge and its time are the statements of the person running the verifier, taken from the processor's records.
L14Headless Oracle operates both the gate whose key signed this log and the witness, so the log and the witness receipt are statements by one party.
L3The witness receipt is Headless Oracle's signed statement that at received_at it was shown a checkpoint signed by the key with that thumbprint; it is only as reliable as Headless Oracle and its signing key. The witness is operated by Headless Oracle, which also publishes the gate software: it is independent of an operator other than Headless Oracle, not of Headless Oracle.

At every stage

"As agent context becomes available, it belongs in the decisions made at every stage"

Ariel Chen, "Securing Agentic Commerce: Why Payment Is Just the Beginning" (https://www.chargeflow.io/blog/securing-agentic-commerce, read 2026-10-26).

The physical order case at three stages, using its two test variants and stating only what their verdicts and data points show:

  • Before fulfilment: variant 2 (we-4-2) reads OUTSIDE-INSTRUCTION, with agent_instruction_scope_ok false and agent_instruction_exceeded refundable_only: a final-sale item, against an instruction that allows only refundable items.
  • If the customer complained: the same values would be available from the same files.
  • If a chargeback followed: variant 1 (we-4-1) reads RECORDED-BEFORE-CHARGE, with its exhibit we-4-1.online.letter.pdf (775084 bytes) and its verdict JSON we-4-1.online-verdict.json (17056 bytes).

The playbook's items

The items of the evidence playbook by Dan Moshkovich, "Agentic Commerce Chargebacks: The Evidence Playbook Merchants Need" (https://www.chargeflow.io/blog/agentic-commerce-chargebacks-the-evidence-playbook-merchants-need, read 2026-10-26), each with what this bundle supplies and the state in variant 1's online verdict:

"Agent identity and signature check"The gate's signed record of which agent key acted. The key's origin, as B-KEY shows it, is headlessoracle.com, the operator itself. A payment network's agent-identity record is not in this bundle.

Two of the playbook's exhibit names: the "mandate record" sits beside the customer's signed instruction, and the "cart as approved compared with the order as placed" beside the cart against the charge. Our exhibit's sections for the customer's signed instruction and for the cart against the charge are in the online exhibits: we-4-1.online.letter.pdf (775084 bytes) and we-4-2.online.letter.pdf (775192 bytes). The playbook's signature verification record is not mapped here: it is a payment network's agent-identity record, not the gate operator's key.
